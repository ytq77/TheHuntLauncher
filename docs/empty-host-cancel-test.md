# 空房取消修复与验证范围

目标版本为 The Hunt preview.7 / preview.8（固定 BBport 1.9.4、BBSC 315f76c）。最初以独立测试补丁验证，preview.9 将此修复一并纳入。

## 已复现的问题

房主已创建匹配房间、应召方始终没有加入时，使用空枪选择“停止唤猎之铃的共鸣”可以停掉搜索，却可能保留旧房主状态。随后改用应猎之铃，效果已生效，但客户端没有发布应召请求。

本轮干净对照已确认：01 房主、02 应召成功进入同一世界，移动和战斗正常。已联机时“停止铃声”灰色，“结束合作”打开玩家名单。房主选中 02 遣返后，服务器 20:26:37 移除客机，20:26:47 结束旧房间，本机回到单人。客机画面返回有滞后；本轮未提供客机详细时间线，未据此认定异常。

## 修复边界

- 只在原版“确认停止唤猎之铃”回调触发时记录取消意图。仅打开空枪菜单、取消对话框、死亡、传送或等待空房，都不会触发。
- 根据用户持有的 CUSA03173 1.09 文件，只读追踪选项 302110 -> 确认对话构造 0x01BC22F0 -> 回调虚表 0x05341300 的 +0x10 -> 0x01BC6BE0。挂接的是 0x01BC6BE7 的完整非相对 store 指令，不移动前面的 RIP 相对指令；签名不匹配则不安装。
- 在游戏线程等原版搜索停止后，仅对同一个会话管理器、房主、自己世界、存活且不在加载、成员数恰为 1、没有远端角色的房间补退房。成员数来自原版 SummonReloadStart 使用的成员计数，保护已入房但角色仍在加载的客机。
- 使用已有的原生 Stop -> RemoteCleanup 流程，不直接写 session state，不全局关闭无缝会话保留补丁。
- 已有成员、成员数据无法读取或操作过期时保留原状；不会把取消动作延迟成之后的一次遣返。

## 已完成的验证

- 固定上游源码生成、中文生成、完整模块编译及存档辅助模块编译通过。
- 原有 111 项 Python 检查通过；原有扫描器、并发页面保护、横幅及灵视退还 C++ 检查通过。
- 新的决策测试和包含实际修复运行时代码的调用测试通过：无明确取消、原版搜索未停、延迟处理、成员仍加载、已有远端角色、错误角色、加载、死亡、不同管理器、数据不可读、过期请求、原生 Stop 拒绝、重复 tick。
- 调用测试使用模拟原生函数，验证调用时机与保护条件；它没有执行游戏中的真实退房，不能替代下面的游戏内验收。
- 本轮 PktMon 产物没有有效游戏数据包，不作为 UDP 互通证据；成功联机的结论来自双方用户确认、服务端加入记录和本机出现一名合作者的记录。

## 尚未完成

10 月 24 日后续实测确认：明确停止唤猎后，原生 Stop 返回成功，会话回到单人，服务器销毁旧房间；同一进程改摇应猎后重新发布应召记录。这部分已通过客户端与服务端记录核对。

同进程交换身份后实际进入对方世界、已有成员在加载中的保护等组合仍待完整实机回归。首次“客机无法加入房主”的根因不因本补丁而被认定已解决。

回归时应先复现“房间已建立但无人成功加入”的状态，取消唤猎后核对本机回到单人、服务器旧房间消失，再在同进程直接使用应猎之铃。已有成员的房间应继续通过“结束合作”名单正常遣返。
